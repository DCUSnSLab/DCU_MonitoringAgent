# GEN-1773: 자리 식별·설치 등록·하드웨어 동기화

## 변경 위치

| 기능 | 새 모듈 | 기존 연결 지점 |
|---|---|---|
| 로컬 식별/DPAPI | `agent/identity.py` | `config.py`의 ID 선택 구간 |
| 선택적 초기 설정 창 | `agent/setup_identity.py` | `main.py --setup [--seat]` |
| Windows 사양 수집 | `agent/collectors/hardware.py` | 등록 작업 스레드에서 호출 |
| 등록/캐시 동기화 | `agent/network/installation.py` | `ApiClient`의 선택적 identity 인자 |
| 서버 설치 인증 | `app/services/installation_service.py` | 보고/종료/구형 등록 진입점 |
| 등록/사양 API | `app/routers/hardware.py` | 라우터 등록 |
| 고정 PK 참조 이관 | `app/reference_migration.py` | 서버 DB 초기화 |
| 운영 이관/설치 관리 | `app/manage_agents.py` | 별도 CLI |

`GEN-1773` 주석으로 기존 코드의 주요 연결 지점을 표시했다. 프론트엔드/탐지 판정/사용량
수집 주기는 변경하지 않는다. ORM/SQL 세부 구조는 migrations/README.md 참조.

## 식별 및 로컬 상태

- `agents` 한 행=한 자리. 별도 자리/본체 테이블 없음.
- 최초 전환: 자리 형식 hostname → 기존 YAML ID → 구형 MAC 기반 자동 ID → 임시 UUID 순서.
- 자리 형식은 `영문·숫자 건물번호-숫자 실습실번호-숫자 자리번호`. 앞자리 0은 보존한다.
- `installation.json`은 설정 YAML 옆에 생성하며 Windows DPAPI **현재 사용자 범위**로 보호한다.
  기본 설치 경로는 `%LOCALAPPDATA%/DCU_MonitoringAgent/`이다. 사용자 계정이 바뀌면 별도
  설치로 취급한다. PC 공통 서비스/HKLM 운영으로 바꾸는 작업은 포함하지 않는다.
- 식별 파일에는 버전, 확정 agent_id, 이전 ID, 설치 UUID, 토큰, 등록 성공 상태를 보관한다.
  토큰은 요청 전 생성/저장하고 서버에는 해시만 보관한다. 성공 응답 유실 후 동일 자격으로
  재시도할 수 있으며, UUID만 아는 사용자가 토큰을 재발급받을 수 없게 했다.
- 손상/복호화 실패는 임의의 새 ID로 자동 승인하지 않고 오류로 중단한다. 원본을 보존하고
  관리자가 복구/기존 설치 폐기 후 재설치한다. 파일 복사 방지는 DPAPI만으로 완전 보장되지
  않으며 관리자 권한/동일 사용자 복제에 대한 한계가 있다.
- `last_synced_hardware.json`은 마지막 저장 성공 구성이다. 시각을 제외하고 정렬한 장치 목록을 비교한다.
- 자동 시작/OTA는 창을 띄우지 않는다. 관리자만 `DCU_MonitoringAgent.exe --setup`으로 창을
  열거나 `--setup --seat D2-535-21`로 무인 초기 지정한다. 기존 식별 파일은 덮어쓰지 않는다.

## 메시지/실패 처리

1. `POST /api/agents/installations`: agent_id, installation_id(UUID), hostname, token.
   상태 active/pending/revoked 반환. 승인 실패 중에도 수집/오프라인 저장은 계속한다.
2. `POST /api/agents/hardware`: 최초/시작 시 변경된 구성 전송. installation_id와
   `X-Installation-Token`으로 승인된 자리인지 검증. hostname/OS, 수집 시각, 총 메모리,
   CPU/GPU/물리디스크/네트워크 목록을 원자적으로 저장한다.
3. `POST /api/agents/report`: 새 클라이언트는 installation_id를 추가하고 hostname/MAC을
   제외한다. IP/상태/탐지/사용량/버전/시각은 유지. 종료 알림도 설치 인증 적용.

모든 전송은 기존 `X-API-Key`도 요구한다. 등록 이후 동일 자리의 다른 설치는 pending이며,
오프라인이라는 이유로 교체하지 않는다. 활성 설치가 있는 자리에 API Key만 보낸 구형 요청은
거부한다. 로컬 값을 다른 자리로 수정해도 토큰-설치-자리 매칭에 실패한다.

하드웨어 조회 실패는 null(기존 보존), 성공했지만 장치 없음은 [](기존 제거). 알 수 없는
속성은 null이다. GPU 내장/외장 구분은 현재 CIM만으로 신뢰할 수 없으면 null을 유지한다.
GPU VRAM은 WMI의 32bit AdapterRAM 대신 드라이버 레지스트리의 64bit 값을 사용하며
제공하지 않는 드라이버에서는 null이다. 메모리는 물리 모듈 Capacity 합계만 저장한다.

등록은 성공까지 재시도, 성공 후 재사용한다. 사양 저장 실패는 등록이 끝난 일반 보고를 막지
않는다. 실패 항목은 다음 재시도에 재조회한다. 버퍼는 원래 수집 시각을 유지하며 현재 탐지
목록은 제외한다. 개수는 기존 offline_buffer_size 설정, 기간은 120일로 제한한다.
버퍼의 이전 ID는 로컬에 보존한 단일 legacy_agent_id와 현재 ID만 재귀속한다. 다른 설치의
버퍼는 전송하지 않는다. 인증된 과거 보고는 최신 상태를 덮어쓰거나 현재 사이트 시간을 늘리지 않는다.

## 서버 설정과 설치 승인

- `AUTO_APPROVE_INSTALLATIONS=false` 기본값: 관리자 승인 필요.
- 신뢰할 수 있는 배포 기간에만 true로 열면 기존 API Key를 가진 첫 설치가 자동 승인된다.
  이미 활성 설치가 있으면 true여도 새 설치는 pending. 전환 후 반드시 false로 닫는다.
- `ALLOW_LEGACY_AGENTS=true` 기본값: 아직 전환하지 않은 자리의 구형 보고 허용.
  전환 완료 후 false로 닫는다. 활성 설치가 있는 자리는 설정과 무관하게 설치 인증이 필요하다.

백엔드 컨테이너에서 아래 명령 실행. 변경 명령은 기본 dry-run이며 `--apply`로만 커밋한다.

```sh
python -m app.manage_agents installations
python -m app.manage_agents approve --installation-id UUID --apply
python -m app.manage_agents revoke --installation-id UUID --apply
python -m app.manage_agents candidates
python -m app.manage_agents create-seat --agent-id D2-535-21 --apply
python -m app.manage_agents merge --source 123 --target 456
python -m app.manage_agents merge --source 123 --target 456 --apply
```

approve는 같은 자리의 기존 활성 설치를 폐기하고 선택한 설치를 승인한다. 이 명령은 운영자의
명시적 교체 결정이다. 일반 사용자용 승인 UI는 추가하지 않았다.

## 기존 데이터 이관/배포

1. 운영 DB 백업 후 복제 DB로 사전 검증. 이 브랜치는 운영 DB에 접속/적용하지 않는다.
2. `2026-11-05_agent_hardware.sql`, `2026-11-05_agent_references.sql` 순서로 적용.
   서버 시작도 같은 추가형 초기화를 수행한다. 참조 backfill은 데이터 크기에 따라 시간이
   걸리므로 운영에서는 사전 점검 시간에 SQL로 먼저 적용한다.
3. 서버를 먼저 배포. 새 배포 환경의 자동 승인 정책을 명시적으로 설정한다.
4. 에이전트 순차 OTA. 새 자리 코드로 저장 시작. 과거 데이터는 별도 merge로 이동한다.
5. candidates 결과를 검토하고 **내부 숫자 PK**로 source/target을 지정한다. 임의명 및
   DESKTOP-*는 위치를 확인하기 전 자동 병합하지 않는다. hostname/agent_id에
   `자리코드-16진수6자리` 접미사가 있으면 자리 코드로 정규화한다. 두 값이 서로 다른
   자리를 가리키면 미확인으로 남긴다. 임의 문자열 접미사는 제거하지 않는다.
6. merge는 원본의 활성 설치/사양이 있거나 분·일 집계가 충돌하면 중단한다. 원본을 버리거나
   겹친 집계를 임의로 합산하지 않는다. 운영자가 원본을 보존하고 기준을 정한 뒤 별도 정리한다.
   충돌 없는 알림/이력은 이동하고 별칭을 남긴다. 전역 이관 잠금과 테이블 쓰기 잠금을 사용하므로
   병합은 점검 시간에 수행한다. 모든 SQL은 한 트랜잭션이며 dry-run은 rollback한다.
7. 문자열 ID는 기존 조회와 호환을 위해 남기되 이력에 `agent_pk` FK를 추가했다. DB 트리거가
   구형/신형 쓰기의 내부 참조를 채운다. 기존 FK/조회 제거는 후속 호환 종료 작업으로 분리한다.
8. 미확인 자리/중복 설치 해결 후 자동 승인과 구형 수용을 닫는다.

DB 변경 전 코드로 롤백할 때는 추가 테이블/컬럼을 삭제할 필요가 없다. 다만 agent_id 병합은
원복 SQL로 추측 복구하지 않고 백업/이관 기록을 사용해야 한다.
